# cimprofiles — splitting the CIM object model out of cim-graph (0.6.0)

**Status:** steps 1–2 of §8 implemented 2026-10-19 (uncommitted): `CIM-Profiles` `rc1` and
CIM-Graph `cimprofiles-0.6`. Written against `profile_writer` @ d403662.
**Goal:** ship the CIM profiles and the I/O-free object model they depend on as a separate PyPI
package, `cimprofiles`. Profile updates (Sparx EA bug tickets, new profiles) then release on their
own cycle, separate from cim-graph fixes (XML writer, UUIDs, NMMS API).

---

## 1. Why split, and why now

| Changes on its own cycle | Changes with cim-graph |
|---|---|
| Generated profiles: EA tickets add or delete classes, and new profiles appear. Regenerated through the CIMTool GUI with `cimantic-graphs.xsl`. | `write_xml`, UUID stability, model authority, NMMS fixes |

- **Why 0.6.0 and not after 1.0.** 1.0 freezes the public API. It should freeze the final
  layout, not a `cimgraph.data_profile` path we already plan to deprecate. Breaking changes are
  acceptable in alpha.
- **One `Identity` for every consumer.** These copies have drifted or depend on cim-graph
  internals today:
  - `CIMGraph-Lite/cimgraph_lite/data_profile/identity.py` is a fork. About 80 lines differ, and
    it lacks model authority, identifier equality (CIM #7540) and class-scoped seeding. It also
    has its own copy of the XSL (`cimtool_xslt/`).
  - CIM-Builder has 36 files that import `cimgraph.data_profile.*`.
  - The CIMHub converters reach profiles through cim-graph (§6).
- **Pinning by profile.** A downstream package can pin a profile version without also pinning a
  cim-graph version (§6).
- **A light install.** `cimprofiles` needs only `pint`. It doesn't pull in the database
  stack (neo4j, mysql-connector, gridappsd-python, SPARQLWrapper).

## 2. What moves where

Dependencies go one way: `cimgraph` depends on `cimprofiles`. `cimprofiles` never imports
`cimgraph`.

| `cimprofiles` (this split) | stays in `cimgraph` |
|---|---|
| `identity.py` (`Identity`, `UUID_Meta`, `stereotype`, `CIMStereotype`, `ARCHIVE_JSON_LD`) | databases, models, fileparsers, writers |
| `units/` (`CIMUnit`, `UnitSymbol`, `UnitMultiplier`, `ureg`, `units.txt`) | `core/env_vars.py`: profile selection, `get_cim_profile()`, the merge memo, `set_model_scope()` |
| `merge.py`, `build_merged_profiles.py`, `dedupe_profile_fields.py`, `merge_releases.yaml` | `core/attribute_utils.py`, `core/serialization.py` |
| `env_vars.py`: `get_model_authority`, `get_model_name`, `get_validation_log_level` and their defaults | |
| `CIM_PROFILE` enum (now `data_profile/__init__.py`) | |
| all generated profiles and their `*.rdfs-t2b.md` | |

`identity.py:9` imports `get_model_authority`, `get_model_name` and `get_validation_log_level`
from `cimgraph.core`. This is the only code dependency from the profiles back into cim-graph.
The three getters move to `cimprofiles.env_vars`, and `cimgraph.core.env_vars` imports them
from there. There must be **one** `@cache` per getter: `set_model_scope()` calls
`cache_clear()`, and with a second copy, `Identity` would keep seeding UUIDs with the old
model scope.

### Name

The distribution name and the import name are both `cimprofiles`: plural, no separator, like
`cimgraph`. On 2026-10-19 `cimprofiles`, `cimprofile`, `cim-profiles` and `cim-profile` were
all free on PyPI. PyPI treats `-`, `_` and `.` as the same character, but dropping the
separator gives a different name: `cim-profiles` is a separate project from `cimprofiles`.
Consider reserving it.

### Repo

`CIM-Profiles` holds the EAP files (Git LFS), the CIMTool workspaces and `CIMTool_plugin/`.
Generated output then lives next to its source.

## 3. Compatibility shims in cim-graph 0.6.0

Two kinds, because they fail in different ways.

### 3.1 `identity` and `units`: alias the module object

Both have module-level state. `ARCHIVE_JSON_LD` is a mutable switch, and `units.py` creates
`ureg = UnitRegistry()`. A star-import shim copies the value of `ARCHIVE_JSON_LD`, so setting
it on the shim would have no effect, with no error. A second copy of `units.py` would create a
second pint registry and raise `Cannot operate with Quantity and Quantity of different
registries`. So alias the module in `cimgraph/data_profile/__init__.py`:

```python
import sys

import cimprofiles.identity
import cimprofiles.units

sys.modules['cimgraph.data_profile.identity'] = cimprofiles.identity
sys.modules['cimgraph.data_profile.units'] = cimprofiles.units
```

`cimgraph.data_profile.identity is cimprofiles.identity`, so a profile generated by an older
CIMTool and one generated by 2.3.1 share the same `Identity` class. Keep the alias **through
1.x**: users' own profiles generated with pre-2.3.1 CIMTool import this path, and we don't
control those files. Pylance can't follow `sys.modules` aliasing. That only affects code
still using the old path.

### 3.2 Generated profiles: star-import re-exports

One shim for each published package path (25 today):

`cgmes_3_0_0` (+ `core_equipment`, `diagram`, `dynamics`, `equipment_boundary`,
`geographical_location`, `operation`, `short_circuit`, `state_variables`,
`steady_state_hypothesis`, `topology`), `cim16v33`, `cim17v40`, `cim18gad`, `cim18gmdm`
(+ `asset`, `canonical`, `connectivity`, `diagram`, `electrical`, `location`, `marketnode`),
`cimhub_2023`, `cimhub_2026`, `rc4_2021`.

```python
# cimgraph/data_profile/cim17v40/__init__.py
import warnings

from cimprofiles.cim17v40 import *
from cimprofiles.cim17v40 import __all__

warnings.warn('cimgraph.data_profile.cim17v40 is deprecated; import cimprofiles.cim17v40',
              DeprecationWarning, stacklevel=2)
```

- `from cimprofiles import cim17v40` is **wrong**. It binds the module, so `cim.ACLineSegment`
  raises `AttributeError`.
- A star import rebinds the same class objects, so `isinstance` and graph keys still work.
  Every generated `__init__.py` already defines `__all__`.
- These shims are removed at 1.0.

### 3.3 cim-graph changes that go with the shims

- `core/env_vars.py::_qualify()`: a bare name resolves to `cimprofiles.<name>`, and the prefix
  `cimgraph.data_profile.` is **rewritten** to `cimprofiles.` before the merge-memo lookup.
  Without that, the comma-specs `cimgraph.data_profile.cim18gmdm.connectivity,...` and
  `cimprofiles.cim18gmdm.connectivity,...` would each build their own merged classes. Objects
  from one would then miss graph keys from the other, with no error.
- `core/env_vars.py`: import the three model-scope getters from `cimprofiles.env_vars`.
  `set_model_scope()` clears the shared caches.
- `utils/mermaid.py:323,389`: `eval(f'{value.__module__}.{name}')` breaks once `__module__` is
  `cimprofiles.*`. Replace it with `getattr(sys.modules[value.__module__], name)`.
- `pyproject.toml`: depend on `cimprofiles`, and remove `cimgraph/data_profile/**` from
  `yapfignore`.
- Internal imports (`xml_parser.py`, `graph_model.py`, `incremental_builder.py`, `mermaid.py`,
  `attribute_utils.py`) move to `cimprofiles.*` directly instead of going through the shims.

## 4. CIMTool 2.3.1 builder changes

Generated code currently has the package path built in at two places:

| File | Emits today | 2.3.1 |
|---|---|---|
| `cimantic-graphs.xsl:89-90` | `from cimgraph.data_profile.identity import Identity, stereotype`, `from cimgraph.data_profile.units import ...` | `from cimprofiles.identity ...`, `from cimprofiles.units ...` |
| `cimantic-graphs-init.xsl:45` | `from cimgraph.data_profile.<envelope>.<envelope> import (` | `from .<envelope> import (` (relative) |

The init change is **required before generated files can go into `cimprofiles`**. Inside
`cimprofiles`, the absolute import resolves to the cim-graph shim, the shim imports
`cimprofiles.<envelope>`, and that circular import fails with "partially initialized module".
A relative import also lets output work from any location.

Until 2.3.1 ships, rewrite **both** lines with `sed` when copying CIMTool output in:
- the init import becomes relative;
- the `identity`/`units` imports become `cimprofiles.*`.

Without the second rewrite, the copied profiles import `cimgraph` and `cimprofiles` can't
stand alone.

The 2.3.1 changes go into `CIMTool-Builders-Library/shipped-builders/cimantic-graphs/`. The
copies in `CIM-Graph/CIMTool_plugin/`, `CIM-Profiles/CIMTool_plugin/` and
`CIMGraph-Lite/cimgraph_lite/data_profile/cimtool_xslt/` should become a single copy (or a
pointer), so they stop drifting.

Optional in the same release: write each class's full UML package path into the existing
`__package__` property (`cimantic-graphs.xsl:458,469-471`), for the reference site (§9). Today
the property returns only the leaf package (`'Wires'`); the change makes it return
`'IEC61970/Base/Wires'`.
- **Building the path:** start from the class's `@packageURI` and follow `a:Package/@basePackage`
  → `a:ParentPackage/@basePackage` up to the root. `rdfs-2020.xsl:50-64` already reads the same
  structure to emit `cims:belongsToCategory`.
- **Safe to change in place:** nothing reads `__package__` today. `merge.py` only copies it
  (`_PROPERTY_NAMES`), and CIM-Builder, the CIMHub converters and Lite never touch it. The leaf
  is still `path.rsplit('/', 1)[-1]`.
- **Verify first:** that CIMTool includes every ancestor `a:Package` in the profile XML, not
  only the leaf packages.

## 5. Pylance and XL profiles (open, needs a spike)

The comma-spec merge was partly a workaround for Pylance on XL profiles: over ~1000
dataclasses in one module, Pylance stops resolving parent-class attributes through `__mro__`
(e.g. `cim17v40`). See `CIM-Builder/cimbuilder/development/PROFILE_RESOLUTION.md` (layer 1).
Moving the profiles into their own package doesn't fix this by itself, but the fix now belongs
in the `cimprofiles` repo. Options:

1. **Stubs.** Ship a `.pyi` per XL profile plus `py.typed`. `merge.py::generate_type_stubs`
   already exists.
2. **One module per UML package**, with `__init__` re-exporting. Each module stays well under
   the limit, and comma-spec merging then only serves real multi-part composition (EQ + SSH +
   TP). Risk: UML packages can inherit from each other in cycles.
   `from __future__ import annotations` covers associations, but base classes need real
   imports, so module order must follow the inheritance graph. If it works, ship it in the
   same CIMTool 2.3.1 release as §4.

## 6. Downstream consumers

| Package | Uses today | After the split |
|---|---|---|
| `CIMHub_2_0/cimhub_core` | `cim-graph>=0.5.0a9`. The floor exists for `units.txt` (pu/USD/Ohm), which is a profile-package concern. | `cimprofiles>=X` for units, plus `cimgraph` only if it uses databases or models |
| `CIMHub_2_0/cimhub_opendss` | `import cimgraph.data_profile.cimhub_2026` (87 sites), `CIMG_CIM_PROFILE=cimhub_2026` | Pin `cimprofiles` to the version its converter is validated against, so a profile update doesn't change converter output by surprise. Imports move to `cimprofiles.cimhub_2026`. |
| `CIMHub_2_0/cimhub_raw` | `CIMG_CIM_PROFILE=cim17v40`. `cimgraph_raw_extension/data_profile/raw_extension.py` extends a profile with `from cimgraph.data_profile.cim17v40 import *` and imports `CIM_PROFILE` from `cimgraph.data_profile` | Pin `cimprofiles` the same way. The extension imports `cimprofiles.cim17v40` and `cimprofiles.CIM_PROFILE`. Test that extension classes still share the base `Identity` (§3.1). |
| CIM-Builder | 36 files on `cimgraph.data_profile.*` | Shims keep it working in 0.6; migrate before 1.0 |
| CIMGraph-Lite | Forked `Identity`, profiles and XSL | Depends on `cimprofiles`, or is retired (§7) |

Converter pins work like this: `cimhub_opendss` pins `cimprofiles==A.B.*`, `cimhub_raw` pins
its own range, and both float on `cimgraph` minor versions. This works because profile
versions are now separate from cim-graph versions.

## 7. Open decisions

- **Database drivers as extras: decided, in 0.6.0.** Extras `sparql`, `neo4j`, `mysql`,
  `gridappsd`, `rdflib` and `all`. `cimgraph.databases` imports each connection on first use
  and names the extra when its driver is missing. Retiring CIMGraph-Lite is still open.
- **Stubs or per-package split** for Pylance (§5).
- **Versioning.** `cimprofiles` follows its own semver, starting at 0.1.0a1. Until 1.0:
  - cim-graph pins `cimprofiles>=0.1.0a1,<0.2`;
  - changes to the `Identity`/metadata contract ship in lockstep.

  At 1.0, loosen the pin to `>=1.0,<2`. From then on, the contract is `cimprofiles` semver:
  - `Identity` internals (`__uuid__`, `UUID_Meta`, `uri()`);
  - field-metadata keys (`type`, `minOccurs`, `maxOccurs`, `serialize`, `inverse`);
  - `CIMStereotype`;
  - `CIMUnit`.

  Breaking any of these means a new `cimprofiles` major version.
- **Seeded UUIDs: decided, `uuid5` in 0.6.0.** `Random(seed)` labeled as version 4 is replaced
  by `uuid5(uuid5(NAMESPACE_URL, authority), '<model>+<ClassName>+<mRID>+<name>+<seed>')`
  (RFC 9562 §5.5; §6.9 says v4 SHOULD come from a CSPRNG). Any language can reproduce it. The
  namespace is derived from the model authority URI (default
  `https://github.com/PNNL-CIM-Tools/CIM-Graph`) and equals the `cim:ModelAuthority` identifier.
  Components are `+`-separated with `%`/`+` escaped, and identifiers are normalized across
  serializations (rules in the cimprofiles README). This ships in the same 0.6.0 break
  as the class-in-seed change, so users see one UUID change, not two. Still open: whether
  `name=` alone should give `uuid4()` (`RELEASE_1_0_PLAN.md`, WS5). If that lands after 0.6,
  it ships as a lockstep release.

## 9. Bonus: profile reference site

A browsable reference for every profile, with one page per class and the differences across
CIM 16 / 17 / 18. It should look more modern than
[Zepben EWB](https://zepben.github.io/evolve/docs/cim/ewb/IEC61970/Base/Core/ConductingEquipment)
or [TNO IEC_CIM](https://ontology.tno.nl/IEC_CIM/cim_ConductingEquipment.html). It would be
hosted on GitHub Pages from the `CIM-Profiles` repo
(`pnnl-cim-tools.github.io/CIM-Profiles/`).

### Source: the Python profiles, not the markdown

| Output | Verdict |
|---|---|
| `*.rdfs-t2b.md` | One file per profile (89k lines for `cim17v40`). Hard to split into pages or diff, and it already has broken anchors (`see [ConductingEquipment](CIM17v40-ConductingEquipment)`, missing `#`). Keep it as a CIMTool artifact, not the site source. |
| AsciiDoc | Same structure problem as the markdown |
| Python profiles | Structured, already shipped, and what users actually import. Introspection gives everything a page needs: docstring, `__mro__`, `@stereotype`, and per-field `type`, `minOccurs`/`maxOccurs`, `inverse`, `namespace`, `stereotypes`. A site built from them can't disagree with the package. |

A script in `cimprofiles` (`docs/build_catalog.py`) introspects each profile into one JSON
catalog per profile: classes, parents, attributes, associations and enums. The site and the
version diff are both built from these catalogs.

### Version comparison

- Diff the catalogs keyed by class name, then by attribute name. Report:
  - classes added or removed;
  - attributes added or removed;
  - type, cardinality or `inverse` changed;
  - namespace moved (e.g. CIM100 → `cim.ucaiug.io/CIM101/draft`);
  - package moved (e.g. `StaticVarCompensator`: Wires → FACTS);
  - docstring changed.
- Renames show up as a remove plus an add. Detecting renames is out of scope.
- Each class page has a "Versions" tab showing which profiles contain the class and the
  attribute-level diff. Each profile pair also gets a summary page, e.g. "cim17v40 → cim18gad:
  N classes added, M removed". This summary can also serve as the review artifact for EA
  ticket regenerations.

### URLs and UML packages

Links must survive new CIM versions, so the class name is the URL key. Packages are not stable
enough:
- **Full paths change between versions:** CIM 17 `IEC61970/Base/...` and `IEC61968/Assets/...`
  become `Grid/Base/...` and `Enterprise/Assets/...` in CIM 18.
- **Leaf packages mostly hold, but not always.** Measured 2026-10-19 across `cim16v33`,
  `cim17v40`, `cim18gad`, `cimhub_2023`, `cimhub_2026`, `rc4_2021`, `cim18gmdm` and
  `cgmes_3_0_0`: of 895 classes in two or more profiles, 50 have a different leaf package in at
  least one.
  - 24 differ only by an `Inf` prefix or `EXT` suffix (`InfAssets` → `Assets`, `Wires` →
    `WiresEXT`).
  - 26 are real moves: `StaticVarCompensator` Wires → FACTS, `Feeder` Core → ContainmentEXT,
    `HeatRate`/`Emission`/`CostPerHeatUnit` Production → Domain, `FunctionBlock` Protection →
    Control, `DCTopologicalNode` Topology → DC.

**Scheme:** the canonical page is `/<Class>/` (cross-version view), with `/<profile>/<Class>/`
for each version. The package appears as a breadcrumb and in the navigation tree, never in the
URL. No redirects to maintain.

**Alternative:** `/<Package>/<Class>/` using the newest profile's leaf package, plus a
`mkdocs-redirects` stub (meta-refresh, works on GitHub Pages) generated from the catalog for
every other package the class has been in. It reads better, but a class's canonical URL
changes whenever it moves, and the redirect list grows with every CIM version.

**Package data:**
- **Today:** `__package__` holds the leaf (`'Wires'`). That's enough for breadcrumbs and a flat
  package list.
- **After CIMTool 2.3.1:** it holds the full path (§4), giving a nested navigation tree. For
  CIM 17 and 18 that is the same class under two different trees.

The catalog script reads the value from the class without creating an instance:
`cls.__package__.fget(None)` (checked on `cimhub_2026`: `ACLineSegment` → `Wires`, `Terminal`
→ `Core`).

### Site stack

- **Recommended: mkdocs-material**, which CIM-Graph's docs already use.
  - `mkdocs-gen-files` writes one page per class from the JSON catalogs.
  - Content tabs hold the version view, and Mermaid draws the inheritance diagrams (the
    markdown builder already emits these).
  - Built-in search, plus the light/dark theme.
  - Watch build time and search-index size at roughly 7k pages (`cim17v40` alone has 1930
    classes).
- **Alternative: Astro + Starlight**, if v1 isn't interactive enough. This would add a
  side-by-side version toggle, a clickable inheritance and association graph, and Pagefind
  search. It's another toolchain (Node), so only move to it for features mkdocs can't do.

### CI

- A GitHub Action builds the catalogs and the site on every `cimprofiles` release tag and
  deploys to Pages.
- Check out with `lfs: false`: the site doesn't need the `.eap` files.
- The site shows the latest release only. Versioned docs per package release (`mike`) are not
  planned.
