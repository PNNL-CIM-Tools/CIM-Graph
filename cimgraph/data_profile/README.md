# CIM Data Profiles

This directory contains the Python data profile modules used by cim-graph.
Each profile is a package of dataclasses generated from a CIM UML export
(via CIMTool or Enterprise Architect Schema Composer).

## How profiles are selected

Set `CIMG_CIM_PROFILE` to the dotted module path of the profile you want:

```bash
export CIMG_CIM_PROFILE="cimhub_2023"
# or fully-qualified:
export CIMG_CIM_PROFILE="cimgraph.data_profile.cimhub_2023"
```

A bare name (no dots) is automatically prefixed with `cimgraph.data_profile.`.

### Multi-profile merge — new in 0.5

Comma-separate two or more sub-profile paths to merge them at runtime:

```bash
export CIMG_CIM_PROFILE="cimgraph.data_profile.cim18gmdm.connectivity,\
cimgraph.data_profile.cim18gmdm.electrical,\
cimgraph.data_profile.cim18gmdm.asset"
```

`get_cim_profile()` calls `merge_profiles()` once and memoises the result.
Every caller in the same process — `XMLFile`, `FeederModel`, any utility
function — receives the **same module object**, so class identity is
maintained across all graph key lookups.

The merged module satisfies the same contract as any single profile: it has
an `__all__` list and each class is accessible via `getattr(merged, name)`.

### cim18gmdm — EPRI GMDM split profile

The GMDM model is split into sub-profiles by functional area. Use the
pre-baked merged package (`cim18gmdm`) for a single-import experience, or
compose the sub-profiles you need at runtime via the comma-spec.

#### Pre-baked merged package

```bash
export CIMG_CIM_PROFILE="cimgraph.data_profile.cim18gmdm"
```

This is a committed `__init__.py` generated by `scripts/build_merged_profiles.py`.
It re-exports all classes from all five sub-profiles (978 classes total) and
is the equivalent of setting the comma-spec to all five sub-profiles.
Use it when you need every profile class available statically (e.g. for
Pylance completion on the full model).

## Loading split exports

For models spread across multiple part files, use an IEC 61970-552 metadata
header (`.cimx` file) to load all parts in one call:

```python
import os
from cimgraph.databases import XMLFile
from cimgraph.models import FeederModel

os.environ['CIMG_CIM_PROFILE'] = (
    'cimgraph.data_profile.cim18gmdm.connectivity,'
    'cimgraph.data_profile.cim18gmdm.electrical,'
    'cimgraph.data_profile.cim18gmdm.asset'
)

# 9500node.cimx lists the individual part files as dcat:Distribution entries.
# XMLFile resolves each accessURL relative to the .cimx file and loads all
# parts into one graph in a single two-pass read.
file    = XMLFile(metadata='profile_parts/9500node.cimx')
network = FeederModel(container=None, connection=file)
```

The `.cimx` format follows IEC 61970-552 §8. Each part file is a
`dcat:Distribution` with an `accessURL` (relative path) and a
`dcterms:conformsTo` URI naming the sub-profile it was written against.

## Adding a custom profile

1. Export your UML profile from CIMTool or Schema Composer as `.xsd`.
2. Run `uv run xsdata generate` (or the equivalent CIMTool builder) to
   produce the dataclass package.
3. Place the generated package under `cimgraph/data_profile/`.
4. Set `CIMG_CIM_PROFILE` to the dotted path of the package.

For split profiles, generate one sub-package per functional area and use
the comma-spec to merge them at runtime.

## Generating a pre-baked `__init__.py` for a split profile

A pre-baked `__init__.py` lets users `import cimgraph.data_profile.<name> as cim`
without knowing the sub-profile names, and lets Pylance/mypy resolve the full
merged class surface statically.

### 1. Register the release in `merge_releases.yaml`

Add an entry to `cimgraph/data_profile/merge_releases.yaml`:

```yaml
releases:
  - name: my_profile          # must match the package directory name
    package: cimgraph.data_profile.my_profile
    parts:
      - cimgraph.data_profile.my_profile.connectivity
      - cimgraph.data_profile.my_profile.electrical
      - cimgraph.data_profile.my_profile.asset
    description: "My profile — merged from connectivity + electrical + asset"
```

`parts` is an ordered list. First-seen order wins for classes that appear in
multiple sub-profiles, so put the most complete sub-profile first.

**Prerequisite — base class consistency:** `merge_profiles` fails fast if two
sub-profiles declare the same class with *different* direct base classes. This
happens when a partial sub-profile uses `Identity` as a stub base for a class
that a fuller sub-profile roots at `IdentifiedObject` or deeper. Fix by
regenerating the offending sub-profile from CIMTool with the full inheritance
chain before running the build script.

To diagnose conflicts before registering:

```python
import importlib
from collections import defaultdict
from cimgraph.data_profile.merge import merge_profiles

parts = ['cimgraph.data_profile.my_profile.connectivity',
         'cimgraph.data_profile.my_profile.electrical']
mods = [importlib.import_module(p) for p in parts]

class_defs = defaultdict(list)
for mod in mods:
    for name in getattr(mod, '__all__', []):
        obj = getattr(mod, name, None)
        if obj and isinstance(obj, type):
            class_defs[name].append(obj)

for name, defs in sorted(class_defs.items()):
    bases = set()
    for cls in defs:
        for base in cls.__mro__[1:]:
            if base is not object:
                bases.add(base.__name__)
                break
    if len(bases) > 1:
        print(f'{name}: conflicting bases {sorted(bases)}')
```

### 2. Run the build script

```bash
python scripts/build_merged_profiles.py
```

This writes a committed `__init__.py` into each package listed in
`merge_releases.yaml` and smoke-tests the import. Re-run after adding or
changing sub-profile parts.

The generated file is a normal Python module — Pylance reads it directly.
It re-exports every class from the appropriate sub-profile, so the source
of each class is traceable and static analysis works without the runtime
merge machinery.

## Runtime merge internals

`cimgraph.data_profile.merge.merge_profiles(*modules)` builds a synthetic
`types.ModuleType` by:

1. Collecting every name from each module's `__all__`.
2. Topologically sorting by inheritance (parents before children).
3. For classes that appear in more than one sub-profile: creating a new
   dataclass with the **union of direct fields**, reparented onto the
   already-merged base class.
4. For classes that appear in only one sub-profile: adopting the class
   as-is but reparenting it onto the merged base if the base was rebuilt.
5. Enums, CIMUnit subclasses, and the shared `Identity` root are taken from
   the first profile that defines them.

The merge fails fast if two sub-profiles declare the same class name with
**different base classes** — that would silently drop a lineage.

To generate a static type-stub file for Pylance/mypy (the replacement for
the hand-maintained `canonical.py`):

```python
from cimgraph.data_profile.cim18gmdm import connectivity, electrical
from cimgraph.data_profile.merge import generate_type_stubs

generate_type_stubs(connectivity, electrical, output_path='cim_merged.pyi')
```
